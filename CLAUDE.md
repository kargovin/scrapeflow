## Goal

A self-hosted, multi-tenant web scraping platform. Primary use case: structured data extraction and change detection to feed ML/data pipelines. Built as a production-grade portfolio project, designed to scale beyond single-user deployments.

---

## Architecture

### Core stack
- **API**: FastAPI (Python)
- **Workers**: Go **http-worker**; Python **Playwright** + **LLM** workers; Python **crawl coordinator**
- **Queue**: NATS JetStream
- **DB**: PostgreSQL (metadata), MinIO (object storage / raw output)
- **Cache / rate limiting**: Redis
- **Gateway**: Traefik
- **Auth**: Clerk (OAuth — Google, GitHub; JWT issued by Clerk, verified by API)
- **MCP server**: LLM-callable interface (scrape_url, get_result, list_jobs)

### Worker contract
Full ADR index and per-record status: `docs/adr/README.md`.
- **ADR-001** — Phase 1 worker contract (partially superseded)
- **ADR-002** — Phase 2 worker contract; authoritative for NATS subjects and message schemas. ⚠️ **Partially superseded 2026-09-03**: its MinIO path convention (**§4** — not §8, which was ADR-001's number for it) is replaced by **ADR-011**
- **ADR-011** — artifact identity; the live path convention (**Accepted 2026-09-03**)

When ADR-001 and ADR-002 conflict, **ADR-002 takes precedence**. On artifact paths, **ADR-011 takes precedence over both**.

## Key decisions

| Concern | Decision | Rationale / trap |
|---|---|---|
| Auth provider | Clerk | Handles OAuth, JWT, user mgmt out of the box |
| Tenancy | Multi-tenant | Each user has isolated jobs/data |
| Scraping engine | HTTP first, Playwright opt-in | Most structured data sites are server-rendered |
| LLM output | User provides own API key + schema | Avoids shared LLM cost; users control their models |
| Output formats | Raw HTML, cleaned Markdown, JSON | Feed directly into ML pipelines |
| Worker design | Light worker — NATS + MinIO only, **no DB access** | ⚠️ **Survives the entire Temporal migration** and is depended on repeatedly: it is why a v1 worker cannot read a lane marker. Keeps workers DB-ignorant; all business logic in the API |
| Job dispatch message | Fat message `{job_id, url, output_format}` | Worker needs no DB lookup to execute the scrape |
| Worker→API result | Worker publishes to `scrapeflow.jobs.result`; API background consumer updates DB | Decoupled; worker never touches Postgres |
| Cross-tenant access | 404 (not 403) for other users' jobs | 403 leaks resource existence |
| NATS subject constants | `app/constants.py`, not `settings.py` | Subject names are part of the worker contract, not env-configurable |
| NATS stream creation | Outside API/worker (init container / infra); API asserts the stream exists at startup | API has no infra concerns |
| Cancellation | API sets `status=cancelled` on active `job_runs` rows; the result consumer discards results for cancelled runs | Worker is unaware of cancellation; the API enforces correctness. (`jobs` has no `status` column after migration 2.4) |
| Rate limiting | Sliding window via Redis sorted set + Lua atomic script | Replaced the fixed-window counter, which allowed a 2× burst; PRD-002 |
| MinIO path convention | **ADR-011 (Accepted 2026-09-03) is the decision.** Artifacts key on **the row that produced them** — `job_runs.id` (job + batch), `crawl_pages.id` (crawl) — carried in one lane-neutral **`artifact_id`** the dispatcher supplies and the worker uses verbatim. Objects are named by **producing stage**: `history/{artifact_id}/scrape.{fmt}`, `history/{artifact_id}/llm.json`, `screenshots/{artifact_id}/{index}.png`. **`latest/` is removed.** `job_runs.result_path` still stores the `history/` path | Supersedes ADR-002 **§4** (dual write keyed on `job_id`, with a `{unix_ts}` object name), which is what BUG-005 is made of: `job_id` is legitimately NULL for batch, so two of three lanes had no honest key. ⚠️ **The key is NOT `run_id`** — the coordinator fabricates one with `uuid4()` for a lane that creates no `job_runs` row, so it names objects after a row that does not exist. ⚠️ **The stage segment is load-bearing**: a flat `history/{artifact_id}.{ext}` silently reintroduces the collision, because `llm-worker` hardcodes `ext="json"` — an `output_format=json` job's LLM output would overwrite its own scraped page. Today the timestamp hides that only because LLM calls are slow. ✅ **Live code implements this as of 2026-09-04, across all three lanes** — but **production still runs the old convention until the next release**, and old objects keep their old-format `result_path` strings forever. **No backfill**: `result_path` is opaque and nothing parses a path, so old objects keep diffing against each other |
| Producer-side NATS message contract | **Two Pydantic models in `api/app/messages.py` — `ScrapeMessage` and `LLMMessage` — are the only way the API publishes.** Every API publish routes through them — and since P9 (2026-09-11) every `ScrapeMessage` is built by one of the two builders in `api/app/core/dispatch.py` (next row); `coordinator/coordinator/messages.py` holds a deliberate duplicate for the crawl lane. **`schema_version` is pinned to `3` and workers reject any other value.** The cross-service contract test lives in `contracts/` and feeds real producer payloads into every worker's real parser, Go's included via committed fixtures | Before this there were **zero producer-side schemas and three consumer-side ones** — which *is* BUG-005 restated. The worker models had not drifted from each other; each said `job_id` was a required string, which is reasonable. They disagreed with a producer that **had no definition to disagree in**. Every suite stayed green because API tests proved the API emits what it emits and worker tests proved each worker parses well-formed messages; **no test ever fed an API-produced message into a worker's parser**. ⚠️ **The Go arm is not optional** — the silent variant (a JSON `null` unmarshalled to `""` with no error) exists *only* on the Python→Go wire, so a Python-only contract test would not reach the failure that actually shipped. ⚠️ **`schema_version` 2→3 is a hard cut, not a compatible extension**: a v2 worker finds no `artifact_id` and a v3 worker finds no `job_id`, so all five services deploy together against a drained stream. A shared contracts *package* was weighed and rejected (ADR-011 §6) — it cannot reach the boundary that broke, and it would factor out a transport the migration deletes |
| Dispatch-message builders | **`api/app/core/dispatch.py` holds one builder per lane — `build_scrape_message(job, run, credentials)` and `build_batch_scrape_message(batch, item, run)` — and every scrape dispatch site calls one of them**: `create_job`, `create_batch`, `_dispatch_due_jobs`, and both branches of `_recover_stale_pending`. No router or loop constructs a `ScrapeMessage` inline. Two tests pin dispatch-vs-recovery **byte equality** per lane | Stale-pending recovery re-publishes a lost run *as-is*, so dispatch and recovery must build the identical message or a recovered run is not the run that was lost. P6 gave the API a shared *model* (what fields exist); it did not give it shared *builders* (what values go in them). `create_job` built inline from the request body, the scheduler from the job row — equal by coincidence, enforced nowhere; the batch lane had no recovery builder at all (BUG-011). ⚠️ `playwright_options` rides only on the playwright engine and is set *inside* the builder, not by the caller — three call sites used to set it separately. ⚠️ **`create_batch` must store `output_format=body.output_format.value`**: with `expire_on_commit=False`, an enum instance assigned to the `VARCHAR` column stays an enum in memory until the post-dispatch refresh, and the builder reads the row before that. Pydantic coerces it today; the row should hold what Postgres holds |
| Worker routing | Subject-based: `scrapeflow.jobs.run.http` (Go), `scrapeflow.jobs.run.playwright` | Workers subscribe to their own subject; the wrong engine never receives the message |
| `nats_stream_seq` | Stored on `job_runs` from the worker's "running" result message | The MaxDeliver advisory carries only stream seq — used to identify stalled runs |
| SSRF re-validation | Re-validated on **every** webhook delivery attempt, not just at job creation | DNS rebinding — the URL can resolve differently at delivery time; PRD-003 |
| Batch data model | New `batches`/`batch_items`; nullable `job_id` on `job_runs` + `batch_item_id` FK, with a mutual-exclusion CHECK. Result consumer routes by which FK is set | ADR-006 Option B — keeps `jobs` template-only, workers unchanged |
| BFS crawl coordinator | Dedicated Python process at `coordinator/`; BFS queue persisted in the `crawl_queue` table | ADR-005 Option B — API rolling deploys must not abort in-progress crawls |
| `jobs.updated_at` | Postgres BEFORE UPDATE trigger, **not** SQLAlchemy `onupdate` | `onupdate` silently skips `db.execute(update(...))` paths (scheduler, cancel route); the trigger fires on every UPDATE |
| API keys uniqueness | `UniqueConstraint(user_id, name)`; `POST /users/api-keys` returns 409 on duplicate | Revoked keys still hold their name — names are identifiers, not recycled |
| Disabling a scheduled job (Q4) | Its **own** operation, not a side effect of `DELETE`: `PATCH /jobs/{id}` `{"schedule_status": "paused"}`. `jobs.schedule_status` is **tri-state** — nullable, `CHECK IN ('active','paused')`, `NULL` = not a scheduled job at all. The scheduler selects only `active` (partial index). `DELETE /jobs/{id}` soft-cancels active `job_runs` only and **never** touches `schedule_status`; hard delete is the explicit `?permanent=true` mode | Cancelling a run and retiring a schedule are different intents — folding them into `DELETE` would make a one-off cancel silently permanent for a recurring job. A bare `is_active` boolean could not express "not scheduled at all". ⚠️ **Migration-critical:** this flag is how the double-lane gotcha is enforced — a job moved to a Temporal Schedule must be paused in v1 or it fires on **both** lanes |
| Page actions field naming | Schema field `actions` → model column `playwright_actions`; popped from the PATCH updates dict and set explicitly | Same pattern as `proxy_url`/`cookies`; consistent with `playwright_options` |
| Action warnings persistence | Worker publishes warnings in the NATS `ResultMessage`; result consumer persists to `job_runs.warnings JSONB`; `GET /jobs/{id}/result` reads the column | Warnings are not stored in MinIO — they live in the result message |
| Webhook event filter | `jobs.webhook_events TEXT[]` (null = all events); checked at every `create_webhook_delivery` call site | Null = no filter (backward compatible); validated against the known event set at the API boundary |
| Content deduplication | `job_runs.content_hash VARCHAR(16)` — xxh64 of raw MinIO bytes; checked in the result consumer before LLM/diff dispatch. On match: `diff_detected=False`, `history/` object deleted, no LLM, no webhook | Regular job path only (not batch, not crawl). Hash stored even with no previous run (first-run baseline); **fail-open** — a hash error skips dedup silently |
| Storage ledger (P8) | **`storage_objects` — one row per MinIO object held for a user; `api/app/core/ledger.py` is the only writer (`record_object`) and the only releaser (`release_*`).** `user_quotas.storage_bytes_used` is a **materialised sum** the ledger moves in the same transaction as the row; `check_storage_quota` still reads it. Idempotency is `UNIQUE (object_key)` with `ON CONFLICT DO NOTHING` — a redelivered result is a no-op, a second artifact for the same run is charged.
