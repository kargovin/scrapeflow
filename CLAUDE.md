## Goal

A self-hosted, multi-tenant web scraping platform. Primary use case: structured data extraction and change detection to feed ML/data pipelines. Built as a production-grade portfolio project, designed to scale beyond single-user deployments.

## Architecture

### Core stack
- **API**: FastAPI (Python)
- **Workers**: Go **http-worker**; Python **Playwright** + **LLM** workers; Python **crawl coordinator**
- **Queue**: NATS JetStream
- **DB**: PostgreSQL (metadata), MinIO (object storage / raw output)
- **Cache / rate limiting**: Redis
- **Gateway**: Traefik
- **Auth**: Clerk (OAuth — Google, GitHub; JWT issued by Clerk, verified by API)
- **MCP server**: LLM-callable interface (scrape_url, get_result, list_jobs)

## Key decisions

| Concern | Decision | Rationale / trap |
|---|---|---|
| Auth provider | Clerk | Handles OAuth, JWT, user mgmt out of the box |
| Tenancy | Multi-tenant | Each user has isolated jobs/data |
| Scraping engine | HTTP first, Playwright opt-in | Most structured data sites are server-rendered |
| LLM output | User provides own API key + schema | Avoids shared LLM cost; users control their models |
| Output formats | Raw HTML, cleaned Markdown, JSON | Feed directly into ML pipelines |
| Worker design | Light worker — NATS + MinIO only, **no DB access** | ⚠️ **Survives the entire Temporal migration** and is depended on repeatedly: it is why a v1 worker cannot read a lane marker. Keeps workers DB-ignorant; all business logic in the API |
| Job dispatch message | Fat message `{job_id, url, output_format}` | Worker needs no DB lookup to execute the scrape |
| Worker→API result | Worker publishes to `scrapeflow.jobs.result`; API background consumer updates DB | Decoupled; worker never touches Postgres |
| Cross-tenant access | 404 (not 403) for other users' jobs | 403 leaks resource existence |
| NATS subject constants | `app/constants.py`, not `settings.py` | Subject names are part of the worker contract, not env-configurable |
| NATS stream creation | Outside API/worker (init container / infra); API asserts the stream exists at startup | API has no infra concerns |
| Cancellation | API sets `status=cancelled` on active `job_runs` rows; the result consumer discards results for cancelled runs | Worker is unaware of cancellation; the API enforces correctness. (`jobs` has no `status` column after migration 2.4) |
| Rate limiting | Sliding window via Redis sorted set + Lua atomic script | Replaced the fixed-window counter, which allowed a 2× burst; PRD-002 |
| MinIO path convention | Dual write: `latest/{job_id}.{ext}` (overwritten) + `history/{job_id}/{unix_ts}.{ext}` (immutable). `job_runs.result_path` always stores the `history/` path | history enables per-run diff; latest is convenience access. ADR-002 **§4** |
| Worker routing | Subject-based: `scrapeflow.jobs.run.http` (Go), `scrapeflow.jobs.run.playwright` | Workers subscribe to their own subject; the wrong engine never receives the message |
| `nats_stream_seq` | Stored on `job_runs` from the worker's "running" result message | The MaxDeliver advisory carries only stream seq — used to identify stalled runs |
| SSRF re-validation | Re-validated on **every** webhook delivery attempt, not just at job creation | DNS rebinding — the URL can resolve differently at delivery time; PRD-003 |
| Batch data model | New `batches`/`batch_items`; nullable `job_id` on `job_runs` + `batch_item_id` FK, with a mutual-exclusion CHECK. Result consumer routes by which FK is set | ADR-006 Option B — keeps `jobs` template-only, workers unchanged |
| BFS crawl coordinator | Dedicated Python process at `coordinator/`; BFS queue persisted in the `crawl_queue` table | ADR-005 Option B — API rolling deploys must not abort in-progress crawls |
| `jobs.updated_at` | Postgres BEFORE UPDATE trigger, **not** SQLAlchemy `onupdate` | `onupdate` silently skips `db.execute(update(...))` paths (scheduler, cancel route); the trigger fires on every UPDATE |
| API keys uniqueness | `UniqueConstraint(user_id, name)`; `POST /users/api-keys` returns 409 on duplicate | Revoked keys still hold their name — names are identifiers, not recycled |
| Disabling a scheduled job (Q4) | Its **own** operation, not a side effect of `DELETE`: `PATCH /jobs/{id}` `{"schedule_status": "paused"}`. `jobs.schedule_status` is **tri-state** — nullable, `CHECK IN ('active','paused')`, `NULL` = not a scheduled job at all. The scheduler selects only `active` (partial index). `DELETE /jobs/{id}` soft-cancels active `job_runs` only and **never** touches `schedule_status`; hard delete is the explicit `?permanent=true` mode | Cancelling a run and retiring a schedule are different intents — folding them into `DELETE` would make a one-off cancel silently permanent for a recurring job. A bare `is_active` boolean could not express "not scheduled at all". ⚠️ **Migration-critical:** this flag is how the double-lane gotcha is enforced — a job moved to a Temporal Schedule must be paused in v1 or it fires on **both** lanes |
| Page actions field naming | Schema field `actions` → model column `playwright_actions`; popped from the PATCH updates dict and set explicitly | Same pattern as `proxy_url`/`cookies`; consistent with `playwright_options` |
| Action warnings persistence | Worker publishes warnings in the NATS `ResultMessage`; result consumer persists to `job_runs.warnings JSONB`; `GET /jobs/{id}/result` reads the column | Warnings are not stored in MinIO — they live in the result message |
| Webhook event filter | `jobs.webhook_events TEXT[]` (null = all events); checked at every `create_webhook_delivery` call site | Null = no filter (backward compatible); validated against the known event set at the API boundary |
| Content deduplication | `job_runs.content_hash VARCHAR(16)` — xxh64 of raw MinIO bytes; checked in the result consumer before LLM/diff dispatch. On match: `diff_detected=False`, `history/` object deleted, no LLM, no webhook | Regular job path only (not batch, not crawl). Hash stored even with no previous run (first-run baseline); **fail-open** — a hash error skips dedup silently |
| Admin result content | Admins read another user's output via a dedicated `GET /admin/jobs/{id}/result`; the user-facing route stays owner-scoped (404 for others). Both share `load_completed_result()` | The owner check can't be relaxed on the user route. `user_email` is joined into the admin `JobResponse` — the `User` model has `email` only, no `name` |
| Frontend asset bundling | Admin SPA served from `/app/` with **no external-CDN dependency** — all assets bundled by Vite. Monaco is configured in `frontend/src/lib/monaco.ts` to use bundled workers, and lazy-loaded | A CDN-loaded dependency breaks offline / under CSP; future frontend deps must bundle locally too. Frontend is on **vite 8 + `@vitejs/plugin-react` 6** (4.x peers only vite ≤7) |
| Admin vs user job views | One set of components (`Jobs`, `JobDetail`, `ResultViewer`) serves both the admin panel (`/app/admin/jobs*`, all users' jobs via `/admin/jobs*`) and the user dashboard (`/app/dashboard/jobs*`, own jobs via owner-scoped `/jobs*`), switched by a `mode: 'admin' \| 'user'` prop — not duplicated. `mode` derives the API base, route base, and result endpoint; admin-only UI renders only when `mode==='admin'`. User Job Detail exposes soft-cancel; admin exposes permanent delete | ~5 localized conditionals per file; duplicating would drift. Backend needed no change — owner-scoped `/jobs*` already 404s cross-tenant, and `user_email` is null there, so the shared column degrades cleanly |
| Frontend admin detection | No role claim on the Clerk JWT — admin status is probed via `/admin/users?limit=1` (200 = admin) in `lib/useIsAdmin.ts` (query key `['admin-check']`), used by `RequireAdmin` (route gate) and `Layout` (nav cross-link) | Backend `/admin/*` authorization is the real gate; the SPA just reacts to 200 vs error. A shared query key means gate + nav read one cached result |
| App shell height | `Layout` root is `h-screen`, not `min-h-screen`; `main` scrolls internally (`overflow-auto`) | `min-h-screen` let tall pages grow the whole page, pushing the sidebar footer below the fold |
| Playwright anti-bot (stealth) | **Patchright** (drop-in Playwright fork) driving **real Google Chrome** (`channel="chrome"`), truly headed under **Xvfb**; launch args `--disable-blink-features=AutomationControlled` (+ `--no-sandbox`, `--disable-dev-shm-usage`); `new_context(no_viewport=True)`; **no UA spoofing**. Env-tunable in `worker/config.py` | Stock headless Chromium failed BrowserScan on webdriver / User-Agent / CDP. Only headed real Chrome yields a clean UA (even `--headless=new` leaks `HeadlessChrome`); the launch arg clears `navigator.webdriver`; Patchright patches the CDP `Runtime.enable` leak. Verified in prod: BrowserScan `Normal`, 0 Robot / 18 checks. Full record: **ADR-008** + `docs/guides/anti-bot-hardening.md` |
| Playwright container start | `entrypoint.sh` — start Xvfb → wait for socket → `exec python` as pid 1. ⚠️ **Never `xvfb-run` as the entrypoint** | `xvfb-run` as pid 1 stays alive after the Python worker dies → the container looks healthy and k8s never restarts a dead worker. `exec python` makes crashes surface as CrashLoopBackOff. Also `ENV PYTHONUNBUFFERED=1` (else crash logs are lost) and pre-create `/tmp/.X11-unix 1777` (Xvfb won't, as non-root). ⚠️ **This contract is the riskiest single item in the Temporal worker port — preserve it exactly** |
| Playwright NATS consumer `ack_wait` | Explicit `ConsumerConfig(ack_wait=120)` on the `python-playwright-worker` pull consumer + `msg.in_progress()` heartbeat every 30s during a job | JetStream's default `ack_wait=30s` < a headed-Chrome scrape (~37s) → redelivery mid-job, a no-op late `ack()`, and with `max_deliver=-1` an **infinite re-scrape loop** (Q6, fired in prod 2026-07-03). The heartbeat covers jobs longer than `ack_wait` |
| LLM NATS consumer `ack_wait` + SDK retry pin | Explicit `ConsumerConfig(ack_wait=120)` + 30s heartbeat, **plus `max_retries=settings.llm_max_retries` (default `0`) pinned on both the `AsyncAnthropic` and `AsyncOpenAI` clients** | Same Q6 bug, worse: `llm_request_timeout_seconds` is 2× the 30s default `ack_wait`, so redelivery fired on ordinary slow calls — and each redelivery re-bills the **user's own** key, unbounded. ⚠️ **The playwright numbers do not transfer**: both SDKs default to `max_retries=2`, so one `call_llm()` could make 3 billable attempts ≈ 210s, past a 120s `ack_wait`. Here **`ack_wait` is the orphan-recovery window, not a job-duration budget**; the heartbeat covers long calls. Raising `llm_max_retries` re-hides retries *beneath* whatever retry layer sits above it and silently multiplies cost and wall-clock |
| Changing a NATS consumer config | **JetStream never applies a changed `ConsumerConfig` to an existing durable.** Procedure: deploy image → confirm pod → `nats consumer rm <STREAM> <DURABLE> -f` → `kubectl rollout restart` → verify with `nats consumer info`. **Delete before restart; never scale to 0** | The worker only calls `pull_subscribe` at startup, so deleting under a running pod leaves it holding a subscription it won't rebuild; scaling to 0 loses to Flux, which reconciles `replicas: 1` straight back. Letting the *worker* recreate the consumer keeps code as the source of truth. Safe because `SCRAPEFLOW` is `--retention work` — verify `Unprocessed`/`Outstanding Acks` are 0 first. ⚠️ **Two verification traps:** the worker's `subscribed` log line prints values from *config*, not from the live consumer (it logged `ack_wait=120` while JetStream ran `30`); and for `max_deliver` only **`nats consumer info --json`** is authoritative — the table output **omits the `Max Deliver` row entirely when the value is `-1`**, so an uncapped and a capped consumer look identical. ⚠️ Between the delete and the restart there is a ~30s window where the old pod is `1/1 Running` and healthy to k8s but consuming nothing |
| LLM cold starts (scale-to-zero) | **Two budgets, do not conflate:** `llm_warmup_max_wait_seconds=180` is the warm-up budget; `llm_request_timeout_seconds` is **60 in `config.py`** and **180 in production** (`LLM_REQUEST_TIMEOUT_SECONDS` in the infra repo's `llm-worker.yaml`; Modal cold start is 90–110s). **+** an `ensure_ready()` warm-up probe against the OpenAI-compatible **`/models`** endpoint before the real call — `openai_compatible` **with** a `base_url` only, 60s process-local warm cache, any HTTP response (incl. 401/404) counts as awake | A cold start exceeded the old 60s read timeout and the worker acked on failure, so the job failed **permanently**. Masked until `llm_max_retries` was pinned to 0 — the SDK's default retries meant a later attempt landed after Modal booted. **The Q6 pin and the timeout bump are safe together and unsafe apart.** `/models` is in the OpenAI spec and implemented by vLLM/Modal; `/health` is not standardised. Anthropic/hosted OpenAI are never probed. ⚠️ **Phase 4:** the activity's start-to-close timeout must exceed *warm-up + request* — **≈360s against production**, not the 240s the repo defaults suggest |
| Bot-wall detection (BUG-003) | `playwright-worker/worker/blocking.py` classifies the rendered page **after `final_url`, before `format_output`**; on a block the worker publishes **`failed` with `error="blocked:<vendor>"`** and does **not** upload the wall. **Tier 1** = vendor challenge harnesses (Akamai, Cloudflare, PerimeterX, DataDome, Imperva, Sucuri, Kasada, Amazon), decisive alone at any size; **Tier 2** = generic challenge language, gated to pages **< 20 KB**; Tier 3 (structural integrity) deliberately unimplemented. Vendor lives in the error string + a `block_detected` log line, not a column | **A block is the server deliberately serving something else because it identified us as a bot — status is evidence, not definition** (the canonical Amazon wall is a **200** with valid HTML). Operative test: *would a human on a normal browser have gotten the real content?* If yes → block; if no → it is the site's honest answer, so **paywalls / login walls / geo-blocks / age gates / genuine 404s are NOT blocks**. ⚠️ Posture is the **inverse** of the LLM classifier: there a wrong "transient" re-bills the user's key, so it fails closed; here a wrong "blocked" fails a working job, so be conservative about *claiming* a block — hence the Tier 2 size gate. ⚠️ **`final_url` is NOT a signal** (Amazon serves the wall at the requested URL). Detection must see **raw HTML** — markdown conversion strips every HTML-level signal. Tier 1/2 patterns adapted from Crawl4AI (Apache-2.0, attribution in `README.md`) |
| LLM transient vs terminal failures | `llm-worker/worker/errors.py` classifies the exception. Transient (timeout, 429, 5xx, MinIO backend fault, MinIO unreachable, warm-up timeout) → `msg.nak(delay=…)` with exponential backoff, **no `failed` published**; terminal (bad/undecryptable key, 400/401/403/404) → publish `failed` + ack. Attempt cap enforced in-worker via `metadata.num_delivered`, with `max_deliver` as the consumer-side backstop. **Unknown exceptions default to terminal** | The worker used to ack on *every* exception, so a cold-start timeout was as permanent as a bad API key. Publishing `failed` on a retry would be locked in by the API's terminal-status guard, which then discards the successful retry — hence only the final attempt reports an outcome, and the **worker** decides when that is, so a run can't dangle in `processing`. Fails closed because the risk is asymmetric: a wrong "transient" retries against the **user's own** key; a wrong "terminal" fails one job. ⚠️ Retry must stay in **one visible layer** — do not restore `llm_max_retries=2` on top of this (3 × 3 = 9 billable calls) |
| Transient MinIO failure = `nak`, not `ack` (all workers) | The LLM classifier, ported to **each** worker: a MinIO **write** fault (result/screenshot upload) is *transient* → `nak` with backoff up to a per-worker attempt cap, publishing terminal `failed` only on the last attempt. Playwright = `playwright-worker/worker/errors.py`; Go = `http-worker/internal/worker/errors.go`. Failures against a **dead target site** (navigation/fetch) stay **terminal** — only *infra* faults retry | Ack-on-failure was latent on all three workers, so a momentary MinIO outage permanently failed a job whose expensive work (headed-Chrome render / paid LLM call) had already succeeded. ⚠️ **The non-obvious trap: "MinIO down" (connection refused) is a different exception class from "MinIO returned a 5xx".** miniopy-async's backend is aiohttp, so unreachable → `aiohttp.ClientConnectionError` (no `.code`), which an `S3Error.code`-only match misses. Go got the same split — `net.Error`/`*url.Error` vs `minio.ErrorResponse.Code`. ⚠️ **Go-specific divergence:** both the `net/http` fetcher and `minio-go` use the net stack, so a dead *site* and a dead *MinIO* both raise `*net.OpError`/`*url.Error` — a bare `net.Error` is ambiguous. So transient-eligibility is scoped to the **upload step**: `processJob` wraps the `Upload()` error in a typed `*uploadError`, and only inside that does `classifyMinIO` apply. Terminal-for-dead-sites is deliberate: a re-scrape costs a headed-Chrome render + proxy bandwidth. Deleted by the migration, but the transient/terminal split is **domain knowledge that ports into the activity** |
| Run status has **two writers**, and the API wins | Status transitions reach the browser as a DB row write plus `pg_notify` **in the same transaction**. Both the background consumer and the API request handlers write and notify — `result_consumer.py` and `quota.py` on the loop side, `routers/jobs.py` and `routers/admin.py` on the request side (both cancellation). **Precedence rule: a cancellation written by the API wins. A write from the result consumer must NEVER move a run out of a terminal state it did not itself set** — `result_consumer.py` checks `run.status == "cancelled"` before anything else, discards the worker's result and re-notifies | ⚠️ **Two writers on one status column fail SILENTLY when the rule is forgotten**: the user cancels a run, watches it cancel, then watches it flip back to `completed`, with the work done and charged. This is deliberate and is preserved into Phase 4 (the v2 mirror activity needs the same guard against `pipeline_runs.status`) — routing cancellation through the workflow would make Cancel *look broken*, since a block is never aborted mid-execution |

## MVP definition

> "Submit a URL via API → get back raw or cleaned data (HTML/Markdown/JSON) → check job status → usable in an ML pipeline"
